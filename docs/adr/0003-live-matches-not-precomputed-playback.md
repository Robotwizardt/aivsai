# 对局运行过程中提供直播

首版对局要在运行过程中向观众展示已发生的过程，而不是先计算完整结果再按时间播放。这个选择优先满足观看比赛逐步产生结果的体验，而不是仅以预计算回放降低流程复杂度；平台因此需要同时处理进行中的比赛、持续产生的记录以及观众连接状态，结束后仍保留回放。

## 比赛与观看相互独立

比赛由服务器独立推进，观众关闭网页、断线或暂停观看均不暂停比赛。暂停只影响该观众的观看进度，重新连接后可以追到直播进度，已结束的比赛则观看回放。

## 故障与成绩

正式对局中，一方策略程序报错或超过运行限额时立即判该方负，并记录错误供外部 Agent 修复；平台或游戏规则执行故障则将对局标为无效，不计排名，不算玩家输。平台必须区分这两类故障，不能将所有执行异常都当成策略失败。

## 容量目标

首版以约 50 人同时在线、正式比赛与训练合计最多 20 场同时运行为设计和验收目标，训练也占用运行容量。超出容量的任务排队，正式比赛优先，同时为训练保留执行机会，并按工作台限制占用，避免一个工作台耗尽全部名额。

按单台服务器可自托管的方向设计，先完成安全与容量测试，再确定服务器配置和费用。选购、实际部署或降低容量目标均需另行确认；这里记录的是待验证的目标，不是已测得的容量或服务器规格承诺。

## 训练采用快速计算

训练用于评估未发布的候选策略，尽快完成计算并返回结果与可分析的回放，默认私密且不计排名，不要求按正式对局的直播节奏推进。正式对局仍在运行过程中直播，不能用训练的快速计算流程预先生成结果后冒充直播。

## 共用执行语义

训练与正式比赛共用规则执行逻辑。正式比赛按节奏推进，训练跳过等待，但两者的逻辑时间、随机机制和策略预算保持一致。不能为了加快训练而改变规则或放宽策略预算，否则训练无法代表正式对战表现。

## 运行中断

运行进程中断后，受影响的运行中比赛标记为无效，不判玩家输，也不计积分；首版不承诺从中途续赛。恢复处理不得重复结算同一场比赛，已完成的有效结算不能因恢复流程再次执行而重复产生积分变动。

相比实现比赛中途恢复，此选择减少首版恢复机制的复杂度，同时要求比赛状态与结算结果能够被可靠区分和核对。

## 实施前的技术验证项

各游戏的直播节奏、队列公平调度的具体实现、工作台占用与请求限额、排队任务的持久化与恢复，以及任务完成和故障判定之间的一致性，仍需在实施设计与验证中确定。不得以平台调度或运行故障冒充策略自身失败。
